=== SISTEMA ===
Você é um engenheiro de testes de software experiente. Você escreve testes unitários em Python com pytest a partir de especificações de regras de negócio.

=== USUÁRIO ===
Você vai criar testes unitários para a função descrita abaixo.
Você NÃO tem acesso ao código da função: baseie-se apenas nas regras de negócio.

## Assinatura
```python
def validate(number, alphabet="0123456789") -> str
```

## Como importar
```python
from alvo import validate, ValidationError, InvalidFormat, InvalidChecksum
```
Exceções que podem ser importadas de `alvo`: ValidationError, InvalidFormat, InvalidChecksum.

## Regras de negócio
# validate (Luhn)

Verifica se um número passa no algoritmo de Luhn (usado, por exemplo, em números de
cartão de crédito).

Exceções (todas podem ser importadas de `alvo`):

- `ValidationError` — base de todas, subclasse de `ValueError`;
- `InvalidFormat` — subclasse de `ValidationError`;
- `InvalidChecksum` — subclasse de `ValidationError`.

## Regras

- **R1** — Se `number` for "falso" em Python (string vazia, `None`, `0`), levanta
  `InvalidFormat`.
- **R2** — Todo caractere de `str(number)` precisa estar em `alphabet` (padrão
  `"0123456789"`); caso contrário, levanta `InvalidFormat`. Não há limpeza de
  separadores: `"7992 7398 713"` → `InvalidFormat`.
- **R3** — Soma de Luhn, com `n = len(alphabet)` e o valor de cada caractere igual à sua
  posição em `alphabet`: percorrendo da direita para a esquerda, os caracteres em
  posições ímpares (1ª, 3ª, …) somam o próprio valor; os em posições pares (2ª, 4ª, …)
  têm o valor dobrado e somam `(2·v) // n + (2·v) % n`. O número é válido quando a soma
  total é múltipla de `n`.
- **R4** — Se a soma não for múltipla de `n`, levanta `InvalidChecksum`:
  `"79927398710"` → `InvalidChecksum`.
- **R5** — Se o número for válido, retorna o próprio `number`, sem alteração e com o mesmo
  tipo recebido: `"79927398713"` → `"79927398713"`.
- **R6** — `alphabet` permite usar outras bases. Por exemplo, com
  `alphabet="0123456789abcdef"` (n = 16), `"1a2b1"` é válido. As letras diferenciam
  maiúsculas de minúsculas.

## Fora do escopo

- Alfabetos com caracteres repetidos.

## O que se espera dos testes
- Cubra todas as regras (R1, R2, …).
- Inclua valores-limite (fronteiras) e entradas inválidas sempre que as regras os definirem.
- Cada expectativa (asserção) deve decorrer das regras. Não invente comportamento que as
  regras não definem e não teste o que está "fora do escopo".
- Indique qual regra cada caso verifica.

## Formato da resposta
Responda APENAS com um objeto JSON (sem texto antes ou depois), no formato:

{"casos": [
  {"id": "C1", "regra": "R1", "tipo": "normal", "descricao": "o que o caso verifica",
   "entrada": {"args": [ ... ], "kwargs": { ... }},
   "esperado": {"retorno": <valor esperado>}},
  {"id": "C2", "regra": "R3", "tipo": "invalida", "descricao": "...",
   "entrada": {"args": [ ... ]},
   "esperado": {"excecao": "NomeDaExcecao"}}
]}

- "tipo" é "normal", "fronteira" ou "invalida".
- "args" e "kwargs" usam valores JSON (números, strings, true/false, null, listas).
- Para valores que JSON não representa, use {"$expr": "<expressão Python>"}, por exemplo
  {"$expr": "float('inf')"} ou {"$expr": "10**30"}. Só são permitidos literais, operações
  aritméticas e as funções float, int, str, bytes, list, tuple, set, dict, bool.
- Em "esperado", use "retorno" (valor que a função deve devolver) OU "excecao" (nome de uma
  exceção embutida do Python ou de uma das exceções listadas acima).
